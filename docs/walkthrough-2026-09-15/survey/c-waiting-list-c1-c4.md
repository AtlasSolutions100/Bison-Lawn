## C1 A waiting-list job is a one-time job with a date WINDOW taken from the service; it only appears on the waiting list when the chosen date is inside its window
Status: partial  Effort: M

### Evidence
DATA MODEL exists: jobs.dispatched / windowStart / windowEnd at lib/db/src/schema/crm.ts:363-366; a waiting-list job = dispatched=false with a window. Services carry defaultStartDate/defaultEndDate (crm.ts:188-189, full yyyy-mm-dd strings), editable on artifacts/bison-crm/src/pages/services.tsx:632-637 (labels 'Default Start Date' / 'Default End Date').

DATE-INSIDE-WINDOW FILTER exists at the API but not in the UI: GET /waiting-list (artifacts/api-server/src/routes/jobs.ts:112-122) filters dispatched=false and, when ?date= is given, windowStart<=date AND windowEnd>=date; ?from/?to do overlap (windowEnd>=from, windowStart<=to). OpenAPI lib/api-spec/openapi.yaml:1051-1074 declares date/from/to. The page artifacts/bison-crm/src/pages/waiting-list.tsx:15-16,31-33 only wires from/to range inputs and with nothing set shows EVERY undispatched job regardless of window (jobs with null windows included). Dashboard count (routes/dashboard.ts:49) is likewise all dispatched=false.

WINDOW FROM THE SERVICE is missing: window jobs are created by generateJobs in routes/clients.ts:260-275 with windowStart=cs.startDate, windowEnd=cs.endDate; those come from the request body or the package (clients.ts:365 startDate, 373 endDate via inherited()), never from services.defaultStartDate/defaultEndDate — repo grep shows those two columns are read only by seed-demo.ts and the services form. The web Assign Service form (pages/client-detail.tsx:1130-1131 state, 1135-1148 prefill from package only, 1173-1176 payload, 1247-1251 required inputs) makes the office type the window by hand each time. The 'window' scheduleType is not validated for missing dates (clients.ts:390-408 validate recurring only) so a window job with null dates is possible; it is invisible under ?date= but shows with no filter. POST /jobs (jobs.ts:144-158, JobInput openapi.yaml:3340-3355) also accepts windowStart/windowEnd directly. Estimate acceptance (lib/schedulingRules.ts:254-258 with resolveSeasonWindow 74-91) derives a window from the scheduling_rules MM-DD columns (crm.ts:694-695), not from the service. Seed data with windows: src/seed-demo.ts:392-402.

### Approach
1) API fallback to the service window: in routes/clients.ts POST /clients/:id/client-services (handler from 317), after computing startDate/endDate (365,373) and when scheduleType==='window', fall back to svc.defaultStartDate/svc.defaultEndDate when both are null; if the resulting end date is before today, roll both forward one year using the same arithmetic as rollDateOneYear in routes/letters.ts:102-107 (extract it into lib/helpers.ts). Return 400 'Window services need a start and end date' if still missing. Keep generateJobs unchanged (it already copies cs.startDate/endDate onto the job). 2) Web prefill: in pages/client-detail.tsx selectItem (1135-1148) add the type==='service' branch: find the service in the already-loaded services list, and when defaultStartDate/defaultEndDate exist set scheduleType('window'), setWindowStart/End from them. 3) Waiting list page: add a single 'Show for date' input (state `date`, default format(new Date(),'yyyy-MM-dd')) passed as { date } to useListWaitingList, plus an 'All dates' toggle that clears it (keeps null-window jobs reachable); keep the from/to range as an advanced option. No spec change needed, ?date= is already declared. 4) Rename the two service form labels to 'Waiting-list window start / end' (services.tsx:633,636) so the office knows what they drive. 5) Test in artifacts/api-server/test/integration.test.ts (or a new creditAndSchedule-style file): insert a service with defaults, POST /clients/:id/client-services { serviceId, scheduleType:'window' } with no dates, assert the job's windowStart/windowEnd equal the service defaults; GET /waiting-list?date=<inside> includes it, ?date=<outside> excludes it.

### Risks
services.defaultStartDate is a fixed yyyy-mm-dd, so it goes stale each season; scheduling_rules already uses MM-DD strings (crm.ts:694-695, schedulingRules.ts:74-91). Either roll forward at assignment time (recommended, minimal) or migrate the two service columns to MM-DD (bigger: services form, OpenAPI Service/ServiceInput 2911-2984, seed-demo). Defaulting the page to today's date hides null-window jobs and jobs whose window has passed; the 'All dates' toggle is what keeps them findable. Packages already inherit their own startDate/endDate (clients.ts:365,373); package values must keep precedence over the service default.

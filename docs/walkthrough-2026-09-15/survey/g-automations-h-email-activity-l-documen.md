## Conventions
MONOREPO: pnpm workspaces; API in artifacts/api-server (Express 5, ESM, tsx for tests, esbuild build), web in artifacts/bison-crm (React 19 + Vite + Tailwind v4 + shadcn under src/components/ui, wouter routing, TanStack Query), DB in lib/db, contract in lib/api-spec. Never edit generated files (ARCHITECTURE.md Gotchas).

API CONTRACT + CODEGEN: lib/api-spec/openapi.yaml is the source of truth (servers url /api; components at line 2283, parameters.IdParam at 2285, schemas from 2291). Every endpoint has an operationId; Orval v8 (lib/api-spec/orval.config.ts) generates (a) React Query hooks + TS types into lib/api-client-react/src/generated/api.ts and api.schemas.ts (exported via lib/api-client-react/src/index.ts, hook names use<OperationIdPascal>, query keys get<OperationId>QueryKey(), fetch through custom-fetch.ts which throws ApiError with the server's `error` message) and (b) Zod request schemas into lib/api-zod/src/generated (named <OperationIdPascal>Body, e.g. CreateWeatherRuleBody, SendSpringLettersBody). Command: `pnpm --filter @workspace/api-spec run codegen` (runs orval then `pnpm -w run typecheck:libs`); then `pnpm run typecheck` at the root. Orval emits zod v4; keep zod on the catalog ^4.

ROUTES: one Router per file in artifacts/api-server/src/routes/*.ts, default-exported and registered in routes/index.ts with router.use(xRouter); the parent mounts at /api (app.ts:107). Order matters: jobsRouter is the first router applying requireAuth to everything reaching it, so any router with PUBLIC paths (webhooks, tracking pixels, public estimate links) must be mounted before jobsRouter and guard its own authed paths by path (routes/index.ts:31-45; pattern: `router.use(['/document-templates', ...], requireAuth, requireAdmin)` as in settings.ts:25 and letters.ts:27, or blanket `router.use(requireAuth, requireAdmin)` as in automation.ts:51). Auth middleware: middlewares/requireAuth.ts (Clerk session -> local users row on req.appUser; requireAdmin checks role==='admin'). Bodies are parsed with the generated Zod schema (`const body = CreateXBody.parse(req.body)`); a ZodError becomes a 400 `{ error }` via app.ts:130-160; other errors 500. Return `{ error: string }` for handled failures. Write audit rows with logAudit({ clientId?, actorName: req.appUser?.name, action, description }) from lib/helpers.ts:18. DB access via `db` from @workspace/db (drizzle, node-postgres pool), tables exported as xxxTable; use db.transaction + .for('update') for claims (see automation.ts:379-432).

EMAIL: all outbound mail goes through the GmailProxy seam in lib/gmail.ts (sendRawGmailMessage; scope is gmail.send only). Reusable senders: sendClientEmailViaGmail (lib/clientEmail.ts:21, text+html, cc/bcc, header-injection checks) — pass an injectable proxy for tests; branded html shells in lib/customerMessageDelivery.ts:29 and lib/letterDelivery.ts:203; logos via brandAssetUrl and company blocks via companyAddressLines/companyContactLine in lib/estimateDocument.ts:151-172; company identity from getCompanyProfile() (lib/companyProfile.ts). Template merge is lib/mergeTokens.ts renderTemplate(body, { client, company, servicesBlock?, quoteTotal? }) with `[token]` syntax; supportedTokens()/unknownTokensIn() feed the UI. Every bulk send is sequential with per-recipient try/catch and a recorded outcome (letterDelivery.ts:313-384 is the model).

SCHEDULING: no cron library. lib/weatherScheduler.ts is the pattern: setInterval tick every 5 min (unref), request hook in app.ts, awaited catch-up on queue read, once-per-local-day claim via INSERT ... ON CONFLICT DO NOTHING on automation_runs (partial unique index on (kind, run_date) where trigger='scheduled'), lease + heartbeat, failed-attempt cap; started in src/index.ts:34; plus a one-shot entry src/jobs/dailyWeatherCheck.ts runnable via `pnpm --filter @workspace/api-server run weather-check` for external cron. New daily automations should reuse this (new `kind` value) rather than a second mechanism.

SCHEMA: edit lib/db/src/schema/crm.ts (pgTable, serial ids, text date-only columns 'YYYY-MM-DD' for calendar dates, timestamp for instants, jsonb with $type, comments explaining why); export types `typeof xTable.$inferSelect`. ## G1 Past-due: 2 days after invoice due date send the "past due" document; 15 days after that send "final notice" (feedback 32, 84)
Status: missing  Effort: L

### Evidence
Nothing evaluates invoice due dates on a schedule and nothing emails a document from one. What exists: invoices carry `dueDate` (lib/db/src/schema/crm.ts:417, date-only string), `terms` snapshot (crm.ts:421) and `sentAt` (crm.ts:425); `dueDateFrom()` (artifacts/api-server/src/lib/invoiceNumbers.ts:52-62) only understands "Net N" and returns null for "Due on receipt"/blank terms, so many invoices will have NO due date. The invoice list route is a plain status/clientId filter with no past-due notion (routes/billing.ts:117-128); invoices.tsx has no due-date/past-due display (grep for dueDate/overdue in invoices.tsx returns nothing). Invoice email send is manual only (routes/billing.ts:271-315 -> lib/invoiceDelivery.ts:23-72, stamps sentAt and audits `invoice_sent`). The ONLY scheduler in the server is the weather one: lib/weatherScheduler.ts:257-272 (5-minute setInterval tick, started from src/index.ts:34), gated by a DB day-claim on `automation_runs` via the partial unique index (kind, run_date) where trigger='scheduled' (crm.ts:547-572) plus lease/heartbeat (weatherScheduler.ts:120-192); it only calls runWeatherCheckForDate (lib/weatherCheck.ts:107). `automation_runs.kind` defaults to "weather" (crm.ts:551) so the same table can carry a second kind. Document templates have kinds notice|estimate_cover|contract only (crm.ts:750-753; openapi.yaml:2641) and the merge tokens (lib/mergeTokens.ts:51-82) know nothing about invoices (no [invoicenumber], [invoicebalance], [invoiceduedate]). BACKLOG.md:95 lists id 32 as open.

### Approach
Build one generic "automated emails" subsystem that G1/G2/G3 all use.

Schema (lib/db/src/schema/crm.ts, then `pnpm --filter @workspace/db run push`):
- `automations`: id serial, name text, kind text ('invoice_past_due' | 'estimate_follow_up' | 'seasonal_notice'), enabled bool default true, offsetDays int default 0 (days after the trigger date), monthDay text null ("09-01", seasonal only), documentTemplateId int references document_templates (set null), sendMode text default 'auto' ('auto' | 'review'), sortOrder int, createdAt/updatedAt. Seed two rows for past-due via an `ensureDefaultAutomations()` in a new lib/automationSeeds.ts modelled on ensureDefaultSchedulingRules (lib/schedulingRules.ts:421) and ensureDocumentTemplates (lib/documentTemplateSeeds.ts:213-244): "Past due notice" offset 2 and "Final notice" offset 17 (2+15), each pointing at a seeded document template of a new kind `automation` (add 'automation' to the kind enum in crm.ts:753 comment, openapi.yaml:2641/2657/2666 and settings.tsx KIND_LABELS/KIND_HELP at ~219-229).
- `email_sends` (shared with H1): id, batchId int null, automationId int null, clientId int references clients cascade, targetType text ('invoice'|'estimate'|'client'|'job'), targetId int null, toEmail text null, subject text, status text ('sent'|'failed'|'no_email'|'pending_review'|'skipped'), error text, gmailMessageId text, trackingToken text unique, openedAt/openCount/lastClickedAt/clickCount, createdAt. Partial unique index on (automationId, targetType, targetId) where automationId is not null so a notice is never sent twice for the same invoice.

Merge tokens: extend `MergeContext` and `buildMap` in lib/mergeTokens.ts:15-82 with an optional `invoice` block -> [invoicenumber], [invoicedate], [invoiceduedate], [invoicetotal], [invoicebalance], [dayspastdue]; and `estimate` -> [estimatenumber], [estimatesentdate] (quotetotal already exists). `supportedTokens()` (mergeTokens.ts:98) then advertises them automatically to the Settings editor.

Runner: new lib/automationRunner.ts with `runAutomationsForDate(today)`: for each enabled automation, select candidates (past_due: invoices status in ('open','partial') AND dueDate IS NOT NULL AND dueDate + offsetDays <= today, join clients; use `todayISO()` from lib/invoiceNumbers.ts:69 for the office day), skip ones with an existing email_sends row for (automationId,'invoice',invoice.id), render subject/body via `renderTemplate` (mergeTokens.ts:110) with company from `getCompanyProfile()` (lib/companyProfile.ts:15), pick `client.billingEmail ?? client.email` for invoice kinds (same precedence as routes/billing.ts:282), send with `sendClientEmailViaGmail` (lib/clientEmail.ts:21, accepts an injectable GmailProxy — keep a `setAutomationGmailProxyForTests` seam exactly like routes/automation.ts:40-48), insert the email_sends row (status sent/failed/no_email), and `logAudit({clientId, actorName: 'Email automation', action: 'automation_email_sent'|'automation_email_failed', ...})` (lib/helpers.ts:18). sendMode 'review' inserts status 'pending_review' rows instead of sending; an admin endpoint POST /automation-emails/:id/send releases one (same claim/outcome pattern as deliverCustomerMessage, routes/automation.ts:498-561).

Scheduling: reuse weatherScheduler's proven mechanics rather than a second timer: in `runDailyWeatherCheck` (weatherScheduler.ts:120) generalise the claim to a `kind` parameter (`automation_runs.kind='emails'`, the unique index is already keyed on kind) and add a second tick target, or copy the file to lib/automationScheduler.ts and start it in src/index.ts next to startWeatherScheduler (index.ts:34). Also add a one-shot `src/jobs/dailyAutomations.ts` + package script like `weather-check` (api-server/package.json:12, jobs/dailyWeatherCheck.ts) so ops can cron it. Fix `dueDateFrom` (invoiceNumbers.ts:52) so "Due on receipt" yields dueDate = invoiceDate (otherwise those invoices can never go past due) — or treat null dueDate as invoiceDate in the runner.

API (lib/api-spec/openapi.yaml, then `pnpm --filter @workspace/api-spec run codegen`): GET/POST /automations, PATCH/DELETE /automations/{id}, POST /automations/{id}/preview (returns who would be emailed today with rendered subject — dry run), POST /automations/run-now, GET /automations/status (mirror WeatherCheckStatus schema at openapi.yaml:3934). Register in a new routes/automated-emails.ts (or in routes/automation.ts under the existing `router.use(requireAuth, requireAdmin)` at automation.ts:51) and add to routes/index.ts.

UI: new panel on artifacts/bison-crm/src/pages/automation.tsx (see G4).

Tests: new test/automatedEmails.test.ts following test/automation.test.ts:1-70 (NODE_ENV=test, TEST_AUTH_TOKEN, x-test-user-id/x-test-auth-token headers, app.listen(0), cleanup in after()); stub Gmail via the proxy seam; assert one send per invoice, no send for paid invoices, final notice only after 17 days, no_email recorded when the client has no address. Add the script to `pnpm test` chain in api-server/package.json.

### Risks
Sending real money-collection emails automatically: a bug sends 400 wrong past-due notices. Default the seeded past-due automations to enabled=false (or sendMode='review') until Adam flips them; the preview/dry-run endpoint must exist before auto mode. Many invoices have null dueDate because terms are blank or "Due on receipt" (invoiceNumbers.ts:52-62) — decide the rule explicitly. `todayISO()` uses America/Los_Angeles while weatherScheduler hardcodes America/Chicago (invoiceNumbers.ts:64-68 note); pick one for the new runner. Partial payments: status 'partial' still has a balance, include it. No do-not-email flag exists on clients yet (grep doNotEmail returns nothing) — K2 dependency; the runner should check it once it exists. `drizzle-kit push` refuses unique constraints on non-empty tables (DEPLOY.md:75-118); a new table is fine but never add a unique index to an existing populated table without the manual ALTER first.

## G2 Seasonal notices to everybody on a date (e.g. sprinkler notice early summer, fall notice on September 1)
Status: partial  Effort: M

### Evidence
A manual, one-template bulk send exists but nothing date-driven and nothing using the document-template library. /spring-letters (artifacts/bison-crm/src/pages/spring-letters.tsx, route in App.tsx:341, nav in components/layout/admin-layout.tsx:34) sends the single-row `letter_templates` letter ({{clientName}}/{{servicesTable}}/{{total}} tokens, crm.ts:590-597, default at lib/letterDelivery.ts:18-33) to selected clients via POST /spring-letters/send (routes/letters.ts:171-174 -> deliverSpringLetters lib/letterDelivery.ts:313-384), sequentially, recording one `letter_sends` row per client (crm.ts:601-610: subject, status sent|failed, error, sentToEmail) and returning {sent, failed, outcomes[]} which the page shows per client (spring-letters.tsx:495-503, RunResults 510-524). Audience is only clients with assigned client_services (letters.ts:49-55), not "everybody". The document_templates library (crm.ts:744-764) can only be rendered for preview (routes/settings.ts:254-281) or attached as PDF to an estimate (routes/estimates.ts:1005-1110); there is no route that emails a document template to a list of clients. No calendar trigger exists anywhere (only the weather tick, weatherScheduler.ts:257).

### Approach
Two pieces, both on the G1 foundation.
1) Generic bulk-send endpoint used by G2, L1 (client/dispatch/waiting-list sends) and H1: POST /document-templates/{id}/send with body { clientIds: number[], jobIds?: number[], subjectOverride?, bodyOverride? } in routes/settings.ts (already guarded by requireAuth/requireAdmin at settings.ts:25). Implementation: create an `email_batches` row (id, kind 'manual'|'automation', documentTemplateId, subject, initiatedByName, recipients int, createdAt), then loop clients exactly like deliverSpringLetters (letterDelivery.ts:328-377: sequential, every step in try/catch, one email_sends row per client, never abort the run), rendering subject/body with renderTemplate + context {client, company} (mergeTokens.ts:110) and optionally a `job` block for tokens like [jobdate]/[servicename] when jobIds are given (extend MergeContext). Send via sendClientEmailViaGmail (clientEmail.ts:21) with html built by wrapping the rendered text in the existing branded shell (reuse createCustomerMessageEmailHtml in lib/customerMessageDelivery.ts:29 or springLetterHtml in letterDelivery.ts:203). Return { batchId, sent, failed, noEmail, outcomes[] } (schema modelled on SpringLetterSendResult openapi.yaml:3755). This gives the "42 of 44 sent" style report for free.
2) Seasonal automation: `automations` row kind 'seasonal_notice' with monthDay ('09-01'), documentTemplateId, audience 'clients' (clients.status='client'); the daily runner (G1) fires it when today's month-day >= monthDay and no email_sends row exists for (automationId, 'client', clientId) with createdAt in the current year (dedupe key: add `periodKey` text column, e.g. '2026', to email_sends and include it in the unique index). Runner calls the same bulk-send function as (1) so counts/logging are identical.
UI: on automation.tsx a "Seasonal notices" entry in the automations panel: name, date (month/day picker), template select (useListDocumentTemplates), enable toggle, "Send now to everyone" button (calls run-now) and last-run line (reuse LastRunLine automation.tsx:177-191). Consider retiring or relabelling the Spring Letters page as "Season renewal" once the generic send exists; leave letter_templates alone (crm.ts:736-743 explains it is kept for that run).

### Risks
"To everybody" needs a definition: clients.status 'client' only, excluding 'lead' and 'former_client' (crm.ts:45); confirm with Adam. Sending ~700 sequential Gmail sends in one HTTP request will exceed proxy timeouts — run bulk sends in the background (insert the batch, respond with batchId, poll GET /email-batches/{id}) or cap per request; the spring-letter run already blocks the request (letters.ts:171). Gmail per-day sending limits (~500/day for standard Workspace, 2,000 for Workspace paid) can be hit by one seasonal blast; record failures with Gmail's error text and allow re-running for the failed subset. Year-dedupe must survive a re-run on the same day.

## H1 Email activity: for each bulk send, delivered count, opened count, click-through to who
Status: missing  Effort: L

### Evidence
There is no unified email log and no delivery/open/click tracking of any kind (grep for openedAt/click/tracking pixel/bounce across api-server, web, spec, db returns nothing). Send outcomes are recorded in five unrelated places: `letter_sends` for spring letters only (crm.ts:601-610, written at letterDelivery.ts:362-368; surfaced per client as lastSendStatus in routes/letters.ts:86-98 and as a one-off RunResults list spring-letters.tsx:510-524 that vanishes on reload); `suggested_actions.messageDeliveryState/messageSentAt/messageGmailId` for approved weather messages (crm.ts:527-533); `estimates.deliveryState/gmailMessageId/sentAt` (crm.ts:293-302); `invoices.sentAt` (crm.ts:425, billing.ts:309); ad-hoc client emails leave only an `audit_events` row action 'client_email_sent' (routes/clients.ts:125-135). Public unauthenticated routes exist as a pattern (routes/estimates.ts:232-300 /public/estimates/:token/respond; routes/index.ts:31-45 explains routers carrying public paths must be mounted before jobsRouter's blanket requireAuth; app.ts:24-31 redacts tokens from logs).

### Approach
1) Data: the `email_batches` + `email_sends` tables from G1/G2 (every sender writes a row: bulk document sends, automations, spring letters, invoice/estimate/client emails — refactor deliverSpringLetters to insert into email_sends as well, or migrate letter_sends). 2) Opens: a public router routes/email-tracking.ts mounted in routes/index.ts BEFORE jobsRouter (next to webRequestsRouter, index.ts:36-45): GET /public/email/o/:token -> updates openedAt (first) and openCount, responds 200 with a 1x1 transparent GIF, Cache-Control: no-store; never 404 (return the gif regardless) and never log the token (extend the redaction in app.ts:24-31 to /api/public/email/...).

## Conventions
Routes: one Express 5 Router per file in artifacts/api-server/src/routes/*.ts, mounted in artifacts/api-server/src/routes/index.ts:27-58 (order matters: jobsRouter is the first to apply a blanket requireAuth, and quickbooks/web-requests are mounted before it for their public callbacks). billing.ts guards with `router.use(["/invoices", "/payments"], requireAuth, requireAdmin)` (billing.ts:37) — any new path prefix (e.g. /audit-events) needs its own guard. Request bodies are validated with zod schemas generated from the OpenAPI spec and imported from @workspace/api-zod, named `<OperationId>Body` (e.g. `UpdateInvoiceBody.parse(req.body)`, billing.ts:13-20,191); a parse failure propagates to the error handler in artifacts/api-server/src/app.ts:146-173 which returns 400 `{ error: "field: message" }`. Query params are read by hand (`req.query as Record<string,string|undefined>`, billing.ts:118). Errors are `res.status(n).json({ error })`; routes throw `Object.assign(new Error(msg), { status })` inside transactions (billing.ts:141). Money: roundMoney (lib/helpers.ts:14); recalcInvoice/recalcClientBalance accept a tx (helpers.ts:131-181); use db.transaction + `.for("update")` and the lock order invoice -> payment -> client (billing.ts:482-486). Audit: `logAudit({ clientId, actorName: req.appUser?.name, action, description })` after the transaction commits (helpers.ts:18-30; billing.ts:175-180). Dates are date-only strings YYYY-MM-DD; use todayISO() for the office timezone (lib/invoiceNumbers.ts:77) and dueDateFrom for terms (52). Invoice number via nextInvoiceNumber(tx) inside the creating transaction (invoiceNumbers.ts:36-42).

## F1 Completed jobs land in an un-invoiced/verify queue where the office edits service, invoice description, service date, rate, quantity, customer notes, adds missed services, and sees account balance vs invoice balance vs total before sending
Status: partial  Effort: L

### Evidence
Completion creates a numbered, itemised invoice immediately and synchronously: artifacts/api-server/src/routes/jobs.ts:562-583 calls createInvoiceForJob (artifacts/api-server/src/lib/invoiceFromJob.ts:34-85) which writes one line per service/product/fee with serviceDate = job.scheduledDate, status 'open', and allocates the next number. Same in vendor-runs.ts:209-230. There is no draft/pending-verification state: invoices.status is only open|paid|partial|void (lib/db/src/schema/crm.ts:394-431) and recalcInvoice (artifacts/api-server/src/lib/helpers.ts:159-181) overwrites status from payments, so a 'draft' status value would be clobbered. sentAt (crm.ts:428) is only stamped after a successful email (billing.ts:309), so the de-facto verify queue is 'open AND sentAt IS NULL', but nothing exposes it: GET /invoices accepts only clientId and status (billing.ts:117-128; lib/api-spec/openapi.yaml:1358-1370) and the page's status select offers only open/partial/paid/void (artifacts/bison-crm/src/pages/invoices.tsx:59-69). Editing: PATCH /invoices/:id (billing.ts:190-243, InvoiceUpdate schema openapi.yaml:3478-3492) already supports replacing all lines (description, serviceDate, quantity, unitPrice), notes, invoiceDate, dueDate, terms, poNumber, status — the API for F1's edits exists — but the UI has no edit control on an existing invoice: InvoiceRow (invoices.tsx:302-394) offers only PDF/Send/Apply Credit/Pay/Void; the line editor exists only inside NewInvoiceDialog for creation (invoices.tsx:118-300). 'Change service': invoice_line_items has no serviceId (crm.ts:442-462); the service line is free text seeded from services.name (invoiceFromJob.ts:62), and services has no invoiceDescription column (crm.ts:176-210: name, description only — B1's domain). 'Add missed jobs': only by typing a line; a second completed job cannot be attached to an existing invoice (invoices.jobId and jobs.invoiceId are single integers, crm.ts:397/178; every completion is its own invoice). Balances: list row shows Total and Balance Due (invoices.tsx:374-379) and 'credit on account' (362-366); the PDF coupon prints Invoice Balance and Account Balance (artifacts/api-server/src/lib/invoiceDocument.ts:311-315); the Invoice API returns server-computed balance (billing.ts:111-112) and Client returns accountBalance + unappliedCredit (artifacts/api-server/src/routes/clients.ts:31-36). No account-balance column in the table. Undo a completion (BACKLOG 70): PATCH /jobs/:id (jobs.ts:447-452) only forbids status=completed; moving completed->scheduled leaves jobs.invoiceId and the invoice intact. BACKLOG.md:44-54 records items 66/35/70 as open.

### Approach
1) Schema (crm.ts invoicesTable): add nullable `verifiedAt: timestamp('verified_at')` and `deliveryMethod: text('delivery_method')` (email|print|both snapshot, see F2). Do NOT add a new status value (recalcInvoice would overwrite it). Leave verifiedAt null in createInvoiceForJob; set it in POST /invoices manual creation only if you want manual invoices to skip the queue (recommend: null everywhere, one queue). Optionally add nullable `serviceId integer references services` to invoiceLineItemsTable so 'change service' is a real selection and reports can attribute lines. 2) OpenAPI + route: extend GET /invoices with `queue` enum [unverified, to_email, to_print, open, past_due] (and `search`, see F3) in openapi.yaml:1358 and billing.ts:117; unverified = verifiedAt IS NULL AND status != 'void'. Add POST /invoices/{id}/verify (operationId verifyInvoice): lock row, set verifiedAt=now, deliveryMethod = client.invoiceDelivery ?? (billingEmail||email ? 'email' : 'print'), logAudit invoice_verified. Add `verifiedAt`, `deliveryMethod`, `accountBalance` (client.accountBalance) to the Invoice schema and hydrateInvoice (billing.ts:89-115 already loads the client). Extend InvoiceLineItemInput with optional serviceId if you add the column; toLineRows (billing.ts:71-85) passes it through. 3) UI invoices.tsx: extract the DraftLine editor from NewInvoiceDialog (lines 118-300) into a shared `InvoiceLinesEditor` component and build `EditInvoiceDialog` that seeds from `invoice.lines` (already in the list response), edits notes/invoiceDate/poNumber/lines, adds a line from a service picker (useListServices; description = service.name, unitPrice = service.rate or GET /services/{id}/price) and saves via useUpdateInvoice({ id, data: { lines, notes, ... } }). Add a 'To verify' tab (queue=unverified) whose rows show Total | Invoice balance (invoice.balance) | Account balance (invoice.accountBalance) plus Edit / Verify buttons; Verify calls useVerifyInvoice and invalidates ['/api/invoices'] and ['/api/clients']. 4) Optional item 70: POST /jobs/{id}/uncomplete (admin): in a transaction lock job + invoice, refuse if invoice.amountPaid>0 or sentAt set (tell the office to void instead), delete the invoice via the M3 delete helper, set job status='scheduled', completedAt=null, invoiceId=null, logAudit job_uncompleted. 5) Tests: new artifacts/api-server/test/invoiceReview.test.ts using the integration.test.ts harness — complete a job, assert it appears under queue=unverified, PATCH lines, verify, assert queue moves to to_email/to_print per client.invoiceDelivery. Register the file in api-server package.json test scripts.

### Risks
Do not introduce a new invoices.status value: recalcInvoice rewrites status from payments and would silently drop it. Changing services.name after the fact never restates existing lines (by design; lines are snapshots). Monthly consolidated invoicing (K4 invoiceFrequency, 'invoices are sent after the last completed job of the month' in the seeded disclosure) is not supported by the one-job-one-invoice model; F1's 'add missed jobs' is only addable as manual lines unless you also build job-to-invoice consolidation (jobs.invoiceId is a bare integer with no FK, crm.ts:178). 'Invoice description' per service depends on B1 adding services.invoiceDescription; until then use services.name. Drizzle push adds the nullable columns cleanly; never run push-force (DEPLOY.md:78-120).

Extend MergeContext with `invoice?: { number, total, balance, accountBalance, invoiceDate, dueDate, terms, poNumber, linesBlock }` and add tokens invoicenumber, invoicetotal, invoicebalance, accountbalance, invoicedate, duedate, invoiceterms, ponumber, invoicelines to buildMap (mergeTokens.ts:50-80) so they appear in GET /merge-tokens automatically. In the send route load the template by key 'bison-bill' (documentTemplatesTable.key), render subject/body with renderTemplate, and pass the rendered body into createInvoiceEmailHtml as a `bodyHtml` param (escape + convert newlines to <p>) placed above the line table; keep today's hard-coded copy as the fallback when the template row is missing. Check the Settings page kind selector accepts the new kind (grep 'estimate_cover' in artifacts/bison-crm/src/pages/settings.tsx). 5) Print: refactor createInvoicePdf into `drawInvoice(doc, data)` so a new GET /invoices/print.pdf?ids=1,2,3 (admin; declare in openapi as application/pdf) renders one PDFDocument with addPage between invoices, stamps printedAt on each, logs one audit line 'Printed N invoices'. UI opens it with window.open like the single PDF. 6) UI invoices.tsx: tabs To verify / To email / To print / Open / All / Payments; row checkboxes with 'Email selected' (sequential useSendInvoice calls, summarise sent/failed like letterDelivery.ts:379-382) and 'Print selected'; Open tab adds columns Due date, Days past due (red when >0), Pays by (paymentMethodPreference or lastPaymentMethod) and a 'Past due only' toggle (queue=past_due). 7) Tests: extend the new invoiceReview.test.ts; unit-test daysPastDue/effectiveDue in invoiceDocument.test.ts style (pure function in invoiceNumbers.ts). G1's past-due automation should consume the same daysPastDue/queue=past_due — tell that builder.

### Risks
Sending is one Gmail call per invoice via the owner's Gmail proxy; a bulk 'email selected' of 100 invoices should run sequentially with a per-invoice result list, not Promise.all. Both 'both' delivery and 'to print' imply two queues can hold the same invoice; define the tab predicates exactly as above so an invoice leaves each queue independently. renderTemplate leaves unknown tokens verbatim (mergeTokens.ts:104-109) so a mistyped token in the Bison bill template reaches customers; the Settings preview (settings.ts:254-282) already reports unknownTokens — surface it. On a hard delete, invoice_line_items cascade (crm.ts:447-449) and payments.invoiceId is set null (crm.ts:465) but jobs.invoiceId is a bare integer with no FK (crm.ts:178) and would dangle.

### Approach
1) API: add DELETE /invoices/{id} (operationId deleteInvoice, 204; declare 409 for refused cases) in billing.ts: db.transaction — lock invoice for update; if sentAt set or amountPaid>0 respond 409 'This invoice was sent/paid; void it instead' unless body/query force=true; detach payments (set invoiceId null, same as the void branch billing.ts:230-233) so money becomes credit; update jobsTable set invoiceId=null where invoiceId=id (job stays completed and reappears in the unbilled_completed_work report, analytics.ts:193-211, so it can be re-invoiced); delete the invoice (lines cascade); recalcClientBalance(clientId, tx); after commit logAudit invoice_deleted with entityType/entityId (F4). Note nextInvoiceNumber is MAX+1 (invoiceNumbers.ts:36-42) so deleting the newest invoice reuses its number, deleting an older one leaves a gap — say so in the confirm text. Add logAudit to DELETE /payments/:id. 2) UI client-detail.tsx: replace ClientInvoices + the Payments button with a ClientAccounting section using Tabs (already imported line 34): header showing Account balance and Unapplied credit (client.unappliedCredit) with 'Add payment' button; Invoices tab table: #number, date, total, paid, balance (invoice.balance), status, actions PDF / Send / Void / Delete (Delete uses useDeleteInvoice with window.confirm); Payments tab: useListPayments({ clientId }) with date, method, reference, invoice #, amount, 'Unapplied credit' tag, Delete (useDeletePayment). Add-payment dialog: amount, method, reference, optional 'Apply to invoice' select of this client's open/partial invoices (none = credit on account), calling useCreatePayment({ data: { clientId, invoiceId: selected ?? null, amount, method, reference } }). Extract RecordPaymentDialog/ApplyCreditDialog/InvoiceSendControls from invoices.tsx into artifacts/bison-crm/src/components/billing/*.tsx and reuse them on both pages rather than duplicating. Invalidate getListInvoicesQueryKey(), getListPaymentsQueryKey(), [`/api/clients/${id}`], ['/api/clients'] and ['/api/clients', id, 'audit']. 3) Tests: add cases to creditAndSchedule.test.ts — delete an unpaid invoice restores balance and nulls job.invoiceId; delete a paid invoice is refused without force and banks the payment as credit with force.

### Risks
Deleting a job's invoice while the job stays completed means the job silently needs re-invoicing; the unbilled_completed_work report is the only surface that shows it unless you also add an 'un-invoiced completed jobs' view (F1). Lock order must stay invoice -> payment -> client (billing.ts:482-486, helpers.ts:131-136) or the delete-payment retry loop can deadlock against it. jobs.invoiceId has no FK, so the manual null-out is mandatory; also check vendor-runs matching (vendor-runs.ts:83-107, 170-173) which treats job.invoiceId != null as 'already invoiced'.

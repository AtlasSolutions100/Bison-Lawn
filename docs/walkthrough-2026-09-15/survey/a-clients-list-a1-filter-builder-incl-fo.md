### Evidence

### Approach

1. In artifacts/bison-crm/src/pages/clients.tsx add `type ClientFilter = { field: FilterField; op: 'contains'|'starts_with'|'equals'|'not_equals'|'is_empty'|'is_not_empty'|'gt'|'lt'; value: string }` and `const [filters, setFilters] = useState<ClientFilter[]>([])`.
2. Field catalogue (typed, from the generated `Client` type in @workspace/api-client-react): name, email, phone, serviceAddress, addressLine2, city, state, postalCode, mapCode, waterDistrict, status, tags (array: contains/equals match any tag), accountBalance (number: equals/gt/lt), billingTerms, invoiceFrequency, invoiceDelivery, accountType, billingEmail, billingCity, nameOnInvoice, accountNumber, createdAt (date: gt/lt), lastServiceDate, plus dynamic `propertyData.<key>` entries collected from all clients' propertyData keys (same useMemo approach as `mapCodes` at :61-68) so 'Turf sqft' style custom fields are filterable.
3. A `FilterBuilder` component in the same file (native <select> for field and operator, <Input> for value, 'Add filter' button, one chip/row per active filter with a remove X, 'Clear all'), rendered under the toolbar at :137-170. Use the same native select styling class as :149 and shadcn Input/Button.
4. Apply filters inside the `visibleClients` useMemo at :70-76 before sorting: string ops case-insensitive on `String(v ?? '')`; number ops with Number(); tags: any element matches. Keep the existing mapCodeFilter as-is (or fold it into the builder as a preset chip).
5. Keep `statusFilter` Tabs and server `search` as they are; the count at :126-132 already reports 'X of Y shown'. Selection already restricts to `visibleIds` (:110-112), so bulk actions naturally act on the filtered set.
6. Optional per-viewer convenience: persist `filters` to localStorage (wrap in try/catch) like dispatch column prefs at artifacts/bison-crm/src/pages/dispatch.tsx:243-251.
7. Add `data-testid` attributes (e.g. `filter-field`, `filter-op`, `filter-value`, `add-filter`) — pages use data-testid for e2e locators (clients.tsx:126, :233).
No server, spec, codegen or drizzle push needed. If a server-side variant is ever wanted (e.g. for pagination), add a `filters` JSON query param to GET /clients in openapi.yaml, parse with zod in clients.ts, and map ops to ilike/eq/sql — not needed now.

### Risks
- All filtering happens on the full list already in memory; fine at ~700 rows but do not add pagination later without moving filters server-side.
- `search` is server-side and `filters` client-side: both apply (AND). Make the UI say 'N of M shown' — already done at :126-132.

### Risks
- Deleting a client cascades invoices and payments (crm.ts:396, :465) — accounting history disappears and QuickBooks-synced records may dangle; hence the refuse-if-invoiced guard and steering the office to 'Former' status instead. The existing single DELETE /clients/:id (:180) has no guard and no audit; consider giving it the same guard.
- Express route order: GET /clients/export must precede GET /clients/:id (clients.ts:82) or it 404s.
- Body 'omit vs null' semantics: zod strips nothing but fills nothing either; read `req.body` with hasOwnProperty like dispatch-map.ts:29-30, otherwise a bulk edit blanks fields the office never touched.
- Tags are stored lowercase (crm.ts:114-120); normalise on add/remove or the search/filters diverge.
- Audit volume: per-client audit rows on a 700-row bulk edit are 700 inserts — acceptable, but do them after the transaction and consider a single multi-row insert instead of `logAudit` in a loop.
- CSV: Excel needs the UTF-8 BOM; escape formula-leading cells; `ids` in a GET query can reach ~4KB for 700 ids (fine under typical 8KB limits, but prefer exporting 'current filter' when all visible rows are selected).
- Codegen must be re-run and `pnpm -w run typecheck:libs` before app typecheck (ARCHITECTURE.md:52); never hand-edit lib/*/src/generated.
- No schema change is needed for any of A2, so no drizzle push and no DEPLOY.md push caveats apply.

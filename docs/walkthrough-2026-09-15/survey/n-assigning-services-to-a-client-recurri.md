## N1 Recurring job: weekly, bi-weekly (odd/even weeks), MONTHLY (week 1 / week 4); assigned contractor so it is always on their board; rate; notes the contractor sees first
Status: partial  Effort: M

### Evidence
Weekly/bi-weekly work today only as an integer 'frequencyWeeks': client_services.frequencyWeeks (lib/db/src/schema/crm.ts:318) and generateJobs in artifacts/api-server/src/routes/clients.ts:276-302 steps `d += frequencyWeeks*7 days` from firstServiceDate until seasonEndDate (cap 60 jobs; with no seasonEndDate only ONE job is created, line 301), inserting jobs with dispatched=true, scheduledDate, amount, budgetedHours — and NO assignedToId and NO notes (lines 290-298). There is no monthly (week-of-month) option anywhere: grep for monthly/weekOfMonth finds only invoiceFrequency. Odd/even is implicit in firstServiceDate and never shown. Rate: amount is set per client-service (clients.ts:344-359: explicit body.amount, else calculatePrice(svc.pricingEquations, body.sqft), else svc.rate*quantity). Contractor: jobs.assignedToId exists (crm.ts:368) and contractor board filters on it (jobs.ts:178-194) but client_services has no assignedToId, so every generated job lands unassigned and must be assigned one by one on the dispatch board. Notes: jobs.notes/notesImportant exist (crm.ts:372-373) and are rendered to the contractor on the job card (artifacts/bison-crm/src/pages/my-jobs.tsx:142-153), but generateJobs never sets them and client_services has no notes column. UI: AddServiceDialog (artifacts/bison-crm/src/pages/client-detail.tsx:1113-1299) has First Service Date, Frequency (weeks) number input (line 1236), Season End Date, Property Sqft, Price Override, Schedule Type; no contractor picker, no notes field, no monthly option. Spec: ClientServiceInput lib/api-spec/openapi.yaml:3070-3088 has no assignedToId/notes/recurrence fields.

### Approach
1) Schema (crm.ts client_services): add `recurrence` text ('weekly'|'biweekly'|'monthly', nullable; keep frequencyWeeks for back-compat: weekly=1, biweekly=2), `weekOfMonth` integer 1-4 (monthly only; weekday taken from firstServiceDate), `assignedToId` integer FK usersTable (onDelete set null), `jobNotes` text, `jobNotesImportant` boolean default false. 2) Move generateJobs out of clients.ts into artifacts/api-server/src/lib/jobGeneration.ts (export it; renewal in N3a and pause/resume in N3g need it). Extend it: for monthly, iterate month by month computing the Nth occurrence of firstServiceDate's weekday in each month (weekOfMonth 4 = 4th, not 'last'); for all recurring types keep the 60 cap and seasonEndDate bound, and ALSO fix the 'no season end => one job' branch (clients.ts:301) by generating e.g. 12 months ahead when seasonEndDate is null, or require seasonEndDate for recurring (simpler; the UI already asks for it). Every inserted job gets assignedToId: cs.assignedToId, notes: cs.jobNotes, notesImportant: cs.jobNotesImportant. Compute and return an `weekParity` ('odd'|'even' ISO week of firstServiceDate) in clientServiceWithName (clients.ts:223-231) for display. 3) Route: POST /clients/:id/client-services (clients.ts:317-459) — read the new body fields via the existing `inherited()` helper (line 360) so packages can also carry defaults; validate weekOfMonth 1-4 when recurrence='monthly'; validate assignedToId is an existing user with role contractor or admin. PATCH /client-services/:id (clients.ts:461-470): when assignedToId or jobNotes change, propagate to this client-service's jobs with status='scheduled' (see N3b). 4) Spec: add the fields to ClientService, ClientServiceInput, ClientServiceUpdate (openapi.yaml:3050-3100); add `assignedToName` to ClientService; run codegen. 5) UI client-detail.tsx AddServiceDialog: replace the numeric 'Frequency (weeks)' with a select Weekly / Every 2 weeks / Monthly; when monthly show a 'Week of month' select (1st..4th) and a derived label 'on <weekday>s'; when biweekly show 'odd/even week' derived from the first date; add a Contractor select (useListUsers + role filter as in waiting-list.tsx:111); add 'Notes for the crew' textarea + 'Important (show first)' checkbox. ClientServices list (client-detail.tsx:1077-1105): show recurrence label, assignedToName, and the notes. Also pass the same fields through NewJobDialog on dispatch (already has assignedToId/notes). 6) Tests: extend creditAndSchedule.test.ts assignService helper cases: monthly generates the Nth weekday per month; assignedToId and notes are copied onto every generated job; biweekly = every 14 days.

### Risks

Return 400 with a clear message when the service is matrix-priced but the client has no value for the field (do not silently fall back to rate — that is the SA failure Adam complained about). Add assignedToId (from N1) to the window insert so a contractor can be pre-assigned; GET /waiting-list already hydrates assignedToName. Spec: ClientServiceInput gets assignedToId; ClientService gets pricedFromLabel/pricedFromValue (nullable). UI (AddServiceDialog): fetch the client (useGetClient is already in scope in ClientDetail; pass `client` down) and prefill the quantity input from client.propertyData for the service's pricing field, label the input with `pricingFieldLabel` returned by POST /services/{id}/price (services.ts:137-143) instead of the hard-coded 'Property Sqft'; prefill Window Start/End from service.defaultStartDate/defaultEndDate (roll to the current/next year with the same logic as resolveSeasonWindow in schedulingRules.ts:74-91); add optional Contractor select. Test: assign a matrix-priced service with no sqft in the body to a client whose propertyData has the field -> amount equals calculatePrice of that value; assign a zone-priced service -> priced against 'Sprinkler Zones', not sqft.

### Risks
Field-label matching is by string label ('Turf Sqft'); if the office renames the estimate field the lookup must follow the id (services.pricingFieldId) — prefer id and only fall back to the literal label for services with pricingFieldId null. Changing the fallback from 'rate*quantity' to a 400 could break the existing package-assignment path where some package members are flat-rate (only apply the strict rule to services with pricingEquations). Keep the /services/{id}/price contract unchanged (it is used by the Services page tester).

## N3g Pause/suspend a service or package (restart when paid or on a date)
Status: missing  Effort: L

### Evidence
No status on client_services (crm.ts:308-329); grep 'pause|suspend' finds nothing outside legal copy (terms.tsx). The only way to stop visits is DELETE /client-services/:id (clients.ts:472-480), which deletes scheduled jobs and the row itself. Jobs can be hidden from the contractor via visibleToContractor (crm.ts:374, JobUpdate openapi.yaml:3371) but that is per job and still shows on the office board. Balance is recomputed in recalcClientBalance (helpers.ts:131-156) after every payment (billing.ts, jobs.ts:419) — a natural hook for 'restart when paid'.

### Approach
Schema client_services: `status` text default 'active' ('active'|'paused'|'cancelled'), `pausedAt` timestamp, `pauseReason` text, `resumeOn` date text, `resumeWhenPaid` boolean default false. Jobs: add status value 'held' to the enum (spec Job/JobUpdate openapi.yaml:3298,3359; nothing in skipPolicy.ts depends on it) and exclude 'held' by default in GET /jobs, /waiting-list, /my/jobs, /my/route (jobs.ts:112-142, 178-211) unless `status=held` is asked for. Endpoints: POST /client-services/:id/pause {reason, resumeOn, resumeWhenPaid} and POST /client-services/:id/resume — in one transaction set the client-service status and flip its jobs status 'scheduled' -> 'held' (only scheduledDate >= today or dispatched=false) / back; audit 'service_paused'/'service_resumed'. Package-level: pause every client_services row sharing packageId for that client. Resume triggers: (a) daily runner (same runner as N3a) resumes rows with resumeOn <= today; (b) after recalcClientBalance in the payment paths (billing.ts POST /payments and /payments/:id/apply, jobs.ts:419) call `resumeIfPaid(clientId, tx)` which resumes rows with resumeWhenPaid when balance <= 0. Spec: ClientService gets status/pausedAt/resumeOn/resumeWhenPaid; new PauseClientServiceInput. UI: Pause/Resume buttons on each ClientServices row with a small dialog (reason, resume date, 'resume when account is paid'); paused rows greyed with the reason; dispatch board filter to show held jobs. Tests: pausing hides jobs from /my/jobs; resume on payment when balance hits zero; resumeOn date runner.

### Risks
A new job status touches every status switch in the web app (dispatch.tsx, my-jobs.tsx status badges) — grep for 'skipped' to find them. Alternative with smaller blast radius: keep status 'scheduled' and add a boolean jobs.held, but every list query still needs the exclusion, so the enum is cleaner. Contractor route optimisation (jobs.ts:196-290) must exclude held jobs. Resuming a recurring service after a long pause may need job regeneration for dates that passed while held — decide: skip them (mark 'skipped' with reason 'paused') rather than dispatching stale dates.

## N4 Time-billed services (cleanups, pruning, sprinkler repair): start/stop time on the job, price adjusted afterwards; fixed-price services keep their rate

### Evidence

### Approach

Jobs: copy `billingMode` and `hourlyRate` at generation (and in POST /jobs / scheduling rules) so a later service edit does not restate a scheduled job. Office override: keep PATCH /jobs/:id amount working (it runs before completion); add a `timeBilledHours` field in the Job response (from entries) so dispatch can show 'clocked 2.4 h → $156' with an 'adjust' input. Fixed services are untouched (billingMode 'fixed' path is the existing code). Spec: Service/ServiceInput/ServiceUpdate gain billingMode/hourlyRate/minimumHours; Job gains billingMode, hourlyRate, clockedMinutes. UI: services.tsx service form (fields around lines 600-660) adds a 'Billed by time' toggle + hourly rate + minimum; dispatch job row shows clocked hours for hourly jobs; contractor job card already shows the clock. Tests: hourly job with two entries of 60+30 min invoices 1.5 h × rate; completion refused while clocked in; fixed job unchanged (extraWork.test.ts:150-176 shows the complete+invoice assertion style).

### Risks
Rounding policy (nearest 15 min? minimum 1 h?) must come from Adam — parameterise via minimumHours and a rounding constant. Multiple contractors on one job each clock separately; summing all users' minutes may double-bill a two-man crew — expose `billedMinutes` and let the office adjust. 'Price adjusted afterwards' in SA also meant editing on the un-invoiced review screen (F1); the pre-completion override covers most of it but an invoice-line editor belongs to F1.

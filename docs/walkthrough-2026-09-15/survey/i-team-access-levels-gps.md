## Conventions

Distances: `haversineKm` and `optimizeRoute` exported from lib/helpers.ts (imported in jobs.ts:23-30). Logger: lib/logger.ts `logger`; per-request `req.log`.

## I1 Contractors with access levels: full user, partial user, mobile-only; a second full user without QuickBooks access (feedback 50, 51, 73, 75)
Status: partial  Effort: M

### Evidence
What exists: exactly two roles. lib/db/src/schema/crm.ts:22 `role: text("role").notNull().default("contractor"), // admin | contractor`, :23 roleSource; lib/ownerAccess.ts:1 `AppRole = "admin" | "contractor"`; OpenAPI AppUser.role enum [admin, contractor] (lib/api-spec/openapi.yaml:2497), AppUserUpdate :2502-2510, InvitationInput :2526-2532. Authorization is one binary gate: requireAuth.ts:179-184 `requireAdmin` (`role !== "admin"` → 403) applied per router (clients.ts:28, billing.ts:37, services.ts:17, estimates.ts:422, reports.ts:10, settings.ts:25, automation.ts:51, dashboard.ts:18, letters.ts:27, vendor-runs.ts:19, web-requests.ts:108, dispatch-map.ts:11, quickbooks.ts:42-52 which guards /quickbooks/status|connect|disconnect|profit-and-loss|expenses). Owner handling: ownerAccess.ts:29-50 recomputes role on every request — only 'owner' and admin/'owner_assigned' survive, everything else collapses to contractor (requireAuth.ts:141-159 writes that back). Team page artifacts/bison-crm/src/pages/team.tsx:268-271 offers only Admin/Contractor in the edit row and :125-132 in the invite form; users.ts:44-104 PATCH /users/:id sets role + roleSource, refuses self-demotion (:55-61) and owner demotion (:75-77), and applies the change to every row of the same person (:67-100). Web gating: App.tsx:244-271 AdminRoute bounces role==='contractor' to /my/jobs; ContractorRoute (:273-291) renders for anyone; the admin sidebar (components/layout/admin-layout.tsx:24-40) is a static list that includes Books (QuickBooks) at :30 with no per-user filtering; pages/books.tsx has no role logic. The 'mobile-only' tier already exists de facto: contractors get ContractorLayout (contractor-layout.tsx:11-14 My Jobs / My Route) and the /my/* API (jobs.ts:178-194 /my/jobs, :196 /my/route, :304-436 offerable services / extra work / on-site payments; time-tracking.ts; photos.ts; field-notes.ts), with contractor-shaped responses (users.ts:25-40 hides email/phone/base). What is missing: no 'partial' tier, no per-area permissions (nothing can deny QuickBooks to an admin), no UI to express three levels, and feedback 73/75 text is only in the feedback table (not in BACKLOG.md; read it with GET /api/feedback as admin before building).

### Approach
Keep `role` binary (it is the shell selector and is checked in ~15 places) and add a permission layer on top of it. (1) Schema crm.ts users: `accessLevel: text("access_level").notNull().default("full")` with values full|partial (meaningful only for role=admin; contractors are mobile-only by definition) and `restrictedAreas: jsonb("restricted_areas").$type<string[]>().notNull().default([])` (area keys: quickbooks, billing, clients, estimates, services, reports, automation, team, settings, letters, dispatch). Optionally the same two columns on invitationsTable so an invite can pre-set them (lib/invitations.ts:71-91 resolveNewAccountAccess then copies them). (2) Server: in middlewares/requireAuth.ts add `requireArea(area: Area)` = requireAdmin + `if (req.appUser.roleSource !== 'owner' && req.appUser.restrictedAreas.includes(area)) 403 {error: 'This area is not enabled for your account'}`; replace `requireAdmin` with `requireArea('quickbooks')` in quickbooks.ts:42-52 (this alone delivers 'second full user without QuickBooks'), and likewise billing.ts:37 ('billing'), reports.ts:10, settings.ts:25, automation.ts:51, users.ts:44/106/110/155/177 ('team'), clients.ts:28, services.ts:17, estimates.ts:422, letters.ts:27. Define the Area union + labels once in a new lib/accessAreas.ts and reuse it in the spec enum. (3) users.ts PATCH: accept accessLevel/restrictedAreas via the generated UpdateUserBody; refuse restricting a roleSource==='owner' row (mirror :75-77); the existing loop :81-100 already applies `body` to every duplicate row. Also add the two fields to the contractor-shaped object at users.ts:27-39 (required fields in the spec must be present). Check lib/userAccounts.ts:76 mergeAccountFields keeps the strongest/least-restricted values when merging duplicates. ownerAccess.ts needs no change because it only touches role/roleSource — do NOT add a third role value there. (4) OpenAPI: add `accessLevel: {enum:[full,partial]}` and `restrictedAreas: {type: array, items: {enum: [...]}}` to AppUser (:2489) and AppUserUpdate (:2502), optionally Invitation/InvitationInput; run codegen. (5) Web: App.tsx AdminRoute gets an optional `area` prop; when `me.restrictedAreas.includes(area)` render a small 'not enabled for your account' card instead of the page (pass area on /books, /invoices, /reports, /settings, /team, /automation, /clients, /services, /estimates, /spring-letters). admin-layout.tsx:24-40: add `area` to each nav item and filter with the ['me'] user. team.tsx UserRow: when role=admin show an Access select (Full / Partial) and, for Partial, a checkbox list of areas (at minimum 'QuickBooks / Books'); mirror in the invite form; update the explanatory copy at team.tsx:22-25 to name the three levels (Full = admin with everything, Partial = admin minus ticked areas, Mobile-only = contractor). (6) Tests: new test/accessLevels.test.ts on the integration harness: admin with restrictedAreas ['quickbooks'] → GET /quickbooks/status 403, GET /dashboard 200, GET /users 200; PATCH restricting an owner row → 400; contractor PATCH /users/:id → 403; add `test:access-levels` to package.json and the `test` chain. (7) Push schema (`pnpm --filter @workspace/db run push`), typecheck, verify in browser as Adam (admin) and as a demo sub, deploy, close feedback 50/51/73/75 with an adminNote.

### Risks
If a builder adds a third `role` value instead of the permission columns, ownerAccess.ts:45-49 resets it to contractor on the next request and the change silently disappears — the recompute at requireAuth.ts:141-159 is the trap. Every hand-built AppUser response (users.ts:27-39, /me at :17-19 returns the raw row) must carry the new required fields or generated types drift. Duplicate-account merges (userAccounts.ts:76-95, users.ts:65) can drop per-user columns unless copied. The Clerk dev instance caps users (TASK-clerk-production-keys.md) — creating real crew logins forces the production-key switch. 'Partial' is only meaningful if every admin router is behind requireArea; a router left on bare requireAdmin stays open to partial users. Feedback 73 and 75 wording is unknown until read from the DB; the level names should match Adam's words (full / partial / mobile-only).

## I2 GPS: see where a contractor is on the dispatch map (at the house / en route) so the office can answer 'where is my guy' without calling (PROMISED)
Status: partial  Effort: L

### Evidence
Foundation only. Coordinates are captured at clock-in/clock-out: schema lib/db/src/schema/crm.ts:843-856 job_time_entries has clockInLat/Lng, clockOutLat/Lng; routes/time-tracking.ts:73-129 and :131-179 store them (body ClockInput lat/lng nullable, openapi.yaml:2391-2399) and put them in the audit description (:117-126); the phone side is pages/my-jobs.tsx:669-687 `currentPosition()` (one-shot navigator.geolocation.getCurrentPosition, 6 s timeout, resolves null on failure) called from TimeClock.punch at :731-741. 'En route' exists only as a job status: my-jobs.tsx:198-214 sets on_the_way/in_progress via PATCH /jobs/:id (jobs.ts:447-510, contractors limited to status/skipReason at :456-466) and the dispatch board shows it as a status badge (dispatch.tsx:548, :590). Nothing live: no table or column for a user's current/last position (users has only baseLat/baseLng, crm.ts:26-27, the home base), no endpoint to report or read positions (grep for watchPosition/lastSeen/location across api-server, bison-crm and the spec returns nothing beyond the clock-in fields), no polling in the web app (no refetchInterval anywhere), and the dispatch map (components/dispatch-map.tsx:113-160) draws only job pins from clientLat/clientLng — its `contractors` prop is {id,name} and there is no crew marker layer. Time entries are per job and admin-visible only via GET /jobs/:id/time-entries (time-tracking.ts:181-190); nothing aggregates 'latest position per contractor'. BACKLOG.md id 49 ('crew is on their way' notification) is adjacent and also unbuilt.

### Approach
(1) Schema crm.ts: new `userLocationsTable` 'user_locations' {id serial, userId int notNull FK users cascade, lat/lng doublePrecision notNull, accuracyM doublePrecision, heading, speedMps, jobId int FK jobs set null, recordedAt timestamp notNull, createdAt default now}; index on (userId, recordedAt). Read latest-per-user with `selectDistinctOn([userLocationsTable.userId])` ordered by userId, recordedAt desc (same pattern as jobs.ts:57-72). Prune rows older than 7 days inside the POST handler (one DELETE, cheap) — privacy and table size. (2) OpenAPI (tag team): `POST /my/location` operationId reportMyLocation, body LocationReport {lat, lng required; accuracyM, heading, speedMps, jobId, recordedAt optional} → 204; `GET /team/locations` operationId listTeamLocations (admin), optional `date` query, → array TeamLocation {userId, userName, lat, lng, accuracyM, recordedAt, ageSeconds, jobId, jobClientName, jobAddress, status enum [at_job, en_route, idle, stale]}. Codegen. (3) Server: new routes/locations.ts, `router.use(requireAuth)`; POST inserts for req.appUser (any role; validate with ReportMyLocationBody; ignore jobId unless canAccessJob-style check passes); GET guarded by requireAdmin (or requireArea('dispatch') once I1 lands): join latest location per user with that user's jobs for `date` (default today) in status on_the_way/in_progress; classify with `haversineKm` from lib/helpers.ts: at_job if within 0.15 km of the client lat/lng of one of their active jobs, en_route if they have an on_the_way job, stale if recordedAt older than 10 min, else idle. Register in routes/index.ts after dispatchMapRouter (:56). (4) Contractor web: new hooks/use-location-reporting.ts used from components/layout/contractor-layout.tsx: consent banner on first use ('Share your location with the office while you are on a job', stored in localStorage), then navigator.geolocation.watchPosition (reuse the null-tolerant, timeout style of my-jobs.tsx:669-687), throttle to one POST /my/location per 30 s and only while useListMyJobs({date: today}) contains a job in on_the_way/in_progress and document.visibilityState==='visible'; stop on visibility hidden / logout; enableHighAccuracy only while on_the_way. (5) Admin web: dispatch.tsx: `useListTeamLocations({date}, { query: { refetchInterval: 30000, enabled: showMap } })`; pass `crew` to DispatchMap; in dispatch-map.tsx add a second `L.layerGroup` for crew so the pin effect (:113-160, which clears the job layer on every render) does not touch it, draw an L.divIcon with initials per contractor coloured by contractor id (define a `contractorColor(id)` helper in a small shared module so D3 per-contractor job colours can reuse it), popup 'Dale · 2 min ago · at 615 E 18th Ave / en route to X', include crew in the fitBounds at :155-158, and grey/strike stale markers; add a 'Crew' strip under the map (or extend SubLoadSummary cards at dispatch.tsx:366-470) with last-seen age and status so the office can answer without opening the map. Also show the last clock-in coordinate from job_time_entries as a fallback 'last seen' when no live report exists. (6) Tests: test/locations.test.ts on the integration harness — contractor POST /my/location 204; admin GET /team/locations returns it with ageSeconds and status at_job when within 150 m of clientWithCoords (lat 32.78/-96.8 at integration.test.ts:96-97) on an on_the_way job; en_route when far; stale when recordedAt is 20 min old; contractor GET → 403. Add `test:locations` script + chain entry. (7) Push schema, typecheck, verify on a phone against the HTTPS deployment (geolocation needs a secure origin), deploy, and tell Adam plainly what it does and does not do (see risks).

### Risks
Be honest with Adam: a browser web app only reports while it is open in the foreground — iOS Safari suspends geolocation when the screen locks or the app is backgrounded, so 'where is my guy' is answered while the sub has Bison Field open (normal during a job) and shows 'last seen N min ago' otherwise; continuous background tracking needs a native app. Geolocation requires HTTPS (production is; localhost is exempt). Privacy/consent: report only during active jobs, show the consent banner, prune history, and never expose positions to other contractors (GET is admin-only; users.ts:25-40 already hides contractor contact data for the same reason). Battery: throttle and use maximumAge. The dispatch map effect at dispatch-map.tsx:113-160 rebuilds markers on selection change — keep crew in its own layer or lasso selection resets. Leaflet marker count is fine (a handful of subs). The Team page and /users list do not need positions; keep them out of AppUser. If I1 ships first, guard GET /team/locations with requireArea('dispatch') rather than bare requireAdmin. Demo subs (HANDOFF.md) have no phones, so a live demo needs a real device signed in as a contractor.
